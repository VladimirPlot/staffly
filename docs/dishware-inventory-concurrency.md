# Совместная инвентаризация посуды

## Контракт сохранения

`GET /api/restaurants/{restaurantId}/inventories/dishware/{inventoryId}` возвращает `version` документа и постоянный `clientKey` каждой строки. Новый клиент создаёт ключ строки один раз и сохраняет его в локальной копии.

`PUT` по тому же адресу требует:

- `expectedVersion`: версия, на основе которой подготовлены изменения;
- `requestId`: UUID конкретной попытки сохранения;
- полное содержимое документа и строки с `id` (для существующих строк) и `clientKey`.

Сервер блокирует строку документа, сверяет версию и сохраняет изменения атомарно. Изменения только строк или фотографий также увеличивают версию. Завершение, возврат в черновик и операции с фотографиями требуют ожидаемую версию. Перемещение и корзина увеличивают версию; скрытый документ нельзя редактировать или менять его фото.

При несовпадении версии возвращается HTTP 409:

```json
{
  "error": "CONFLICT",
  "message": "Инвентаризацию изменил другой менеджер...",
  "meta": {
    "type": "DISHWARE_VERSION_CONFLICT",
    "current": { "id": 123, "version": 8, "items": [] }
  }
}
```

Автосохранение приостанавливается. Клиент сравнивает исходную копию, локальный ввод и текущую серверную копию. Выбранный результат отправляется с версией показанной серверной копии. Если она снова изменилась, появляется новая сводка; безусловного обхода проверки версии нет.

## Правила сведения

Оба варианта сохраняют независимые изменения разных полей и строк, включая новые строки другого менеджера. Совпадающие названия не означают одну позицию: строки сопоставляются по постоянному ключу.

| Ситуация | Перезаписать результаты | Сложить результаты |
| --- | --- | --- |
| «Стало» изменил один менеджер | Его значение | Его значение |
| «Стало» изменили оба | Локальное значение | Сумма двух пересчётов, даже если значения равны |
| «Было», приход, цена, название изменены обоими | Локальное значение | Локальное значение, без сложения |
| Разные заметки/комментарии изменены обоими | Локальный текст | Оба текста через пустую строку |
| Строка удалена на сервере, локально не изменена | Остаётся удалённой | Остаётся удалённой |
| Строка удалена на сервере, локально изменена | Восстанавливается с новым ID | Восстанавливается с новым ID |
| Локально удалена строка, изменённая на сервере | Удаляется | Сохраняется серверная строка |
| Новые строки с разных устройств | Сохраняются обе | Сохраняются обе |

Фото окончательно удалённой строки не восстанавливается; это указано в сводке. Превышение лимита количества, числа строк или длины объединённого текста блокирует соответствующий вариант, без обрезания. У старой локальной копии без исходного снимка сложение недоступно.

«Отмена» сохраняет локальный ввод и приостанавливает автосохранение. Следующее ручное сохранение снова открывает сводку. Если другой менеджер завершил документ, его нельзя перезаписать: локальная копия сохраняется до явного выбора актуального документа.

## Потеря ответа и повторная отправка

Перед отправкой на устройстве сохраняются UUID операции, исходный ввод и точный выбранный результат. При повторе отправляется тот же запрос. Сервер хранит небольшой чек операции: UUID, хеш запроса и применённую версию. Повтор одного UUID с другим содержимым отклоняется.

Если после принятой операции документ не менялся, повтор возвращает текущий документ без записи. Если менялся, HTTP 409 дополнительно содержит `alreadyApplied: true` и `appliedVersion`. Клиент принимает уже отправленный результат за новую исходную копию; собственная сумма не прибавляется повторно. Чеки удаляются вместе с документом.

## Корзина и ошибки

При восстановлении документа или папки внутри скрытого предка объект перемещается в корень. Предки остаются в корзине. Интерфейс предупреждает до восстановления и сообщает фактический результат после ответа сервера.

Ошибки загрузки корзины очищают устаревший список и показывают повтор загрузки вместо сообщения о пустой корзине. Ошибки восстановления и удаления остаются видны в окне подтверждения. После частичного сбоя очистки корзины список перечитывается после завершения всех запросов.

## Фото новых позиций

Фото новой позиции можно выбрать до её первого сохранения, в том числе до заполнения названия. Перед добавлением открывается общее с карточками базы знаний окно кадрирования. После подтверждения миниатюра и полное фото атомарно сохраняются под одним ключом IndexedDB, а локальный черновик содержит только ссылку и метаданные. Отмена кадрирования сохраняет прежнее фото. Это позволяет восстановить обе версии после перезагрузки, не расходуя лимит localStorage на изображения. Старые локальные записи с единственным Blob продолжают читаться.

Сохранение сначала получает ID строк, затем последовательно отправляет выбранные фото с актуальной версией документа. Ошибка загрузки оставляет фото в очереди; повтор не создаёт строку заново. Сведение конфликтов сохраняет локальные фото, завершение и выход с сохранением дожидаются их загрузки. Замена, удаление, успешная отправка и выход без сохранения освобождают ненужные локальные файлы. Форматы и лимит совпадают с сервером: JPEG/PNG/WebP, до 2 МиБ.

Исходник с камеры может занимать до 20 МиБ (до 40 Мп). Общая с базой знаний обработка создаёт квадратное превью 512×512 до 256 КиБ и полное изображение без кадрирования до 2048 px по длинной стороне и до 1 МиБ. Это оптимизированная копия, а не архив исходного файла. Оба файла вместе помещаются в действующий лимит multipart-запроса 2 МиБ.

Миграция `V139__dishware_original_photos.sql` добавляет `original_photo_url`. В POST фото необязательный `originalFile` отправляется вместе с `file`; сервер сохраняет пару одним изменением версии. При сбое второй загрузки транзакция откатывается и первая загрузка очищается. При замене, удалении строки/документа и копировании в новый период учитываются обе версии. Без нового файла полное фото открывается из прежнего `photoUrl`.

Полное фото загружается только при открытии просмотра. Общий просмотрщик поддерживает щипок, перетаскивание, колесо/тачпад, ползунок, клавиатуру и сброс. Просматривать завершённые документы можно; заменять и удалять их фото нельзя. На телефоне кнопки замены/удаления находятся в просмотрщике, меню поверх миниатюры отсутствует. На компьютере меню появляется при наведении/фокусе.

## Мобильный подсчёт

До 640 px таблица заменяется карточками без горизонтальной прокрутки. Фото с номером в левом верхнем углу занимает первые три строки слева; название справа занимает две строки фиксированной высоты. Третья строка справа содержит цену, денежный результат и кнопки заметки/удаления. Четвёртая строка на всю ширину — «Было», «Приход», «Стало». Название уменьшается от 14 до 12 px, длинные слова переносятся; нажатие открывает полное название. Ввод названий на телефоне и компьютере ограничен 50 символами, ранее сохранённые названия сохраняются без обрезания. Крупный денежный результат можно открыть целиком нажатием. Enter/«Далее» из «Стало» переводит к следующей позиции; на последней завершает ввод. При переходе к настольному размеру восстанавливается обычная таблица с теми же данными.

## Фиксация, исправления и периоды

Сохранение (в том числе автоматическое) сохраняет черновик; «Завершить» фиксирует результат. Сервер запрещает изменение данных и фото завершённого документа. Возврат в черновик требует актуальную версию и непустую причину до 1000 символов. После такого возврата постоянная отметка `hasCorrections` видна в списке и редакторе, в том числе после повторного завершения.

«С нуля» создаёт пустой независимый документ. «На основе» разрешено только для завершённого источника: прошлое `currentQty` становится `previousQty`, приход и новый пересчёт начинаются с нуля. Цены, названия, заметки и копии фото сохраняются. Исправлять источник разрешено и после создания следующего периода. Скопированные остатки последующих документов автоматически не изменяются; об этом есть предупреждение при исправлении и подпись рядом с источником.

Миграция `V138__dishware_history_and_surplus.sql` добавляет серверный журнал. Создание, сохранение, завершение, возврат для исправления, фото, перемещение, корзина, восстановление и окончательное удаление фиксируют автора (ID и имя на момент действия), время, действие, причину и полные снимки до/после. Запись истории находится в той же транзакции, что и изменение; повтор уже принятого `requestId` не создаёт повторную запись. История сохраняется после окончательного удаления документа. История до установки функции не восстанавливается задним числом. Старые файлы фото при замене по-прежнему удаляются: снимки фиксируют факт изменения и URL, но не архивируют бинарные изображения.

`GET /api/restaurants/{restaurantId}/inventories/dishware/{inventoryId}/history?beforeId=...` доступен менеджерам своего ресторана, возвращает до 30 записей по убыванию ID. Следующая страница использует ID последней записи. Методов изменения/удаления записей журнала нет.

## Учёт излишков

`includeSurplus` по умолчанию `false`, в том числе у существующих документов после миграции. При выключенном флаге каждая строка даёт `max(Было + Приход − Стало, 0) × Цена`; излишки другой строки не компенсируют недостачу. Фактическое количество излишков остаётся видимым.

При включённом флаге сумма строки равна `(Было + Приход − Стало) × Цена`, сумма документа может быть отрицательной (положительный баланс для ресторана). В API `totalLossAmount` и `totalLossQty` тогда содержат подписанный нетто-результат; строковые `lossQty`/`gainQty` остаются фактической недостачей/излишком. Интерфейс показывает денежный баланс с противоположным знаком: потери со знаком минус, положительный баланс со знаком плюс. Флаг сохраняется в черновике, восстанавливается после перезагрузки, участвует в проверке версии, трёхстороннем объединении и истории.

Отсутствующий `includeSurplus` в запросе сохраняет текущую настройку (совместимость со старыми клиентами). Для старых незавершённых сохранений без этого поля сохранён прежний алгоритм хеширования квитанции. Возврат в черновик без причины теперь отклоняется — старый клиент должен обновиться.
