# Общие графики

Общий график — отдельное представление опубликованных графиков одного ресторана.
Хранятся только название, флаг видимости, версия настроек и упорядоченные ссылки
на источники. Строки, смены, участники и история не копируются.

## Правила

- Создание, изменение настроек и удаление доступны Manager+.
- Требуются минимум два разных опубликованных источника.
- Первый источник задаёт период. Остальные целиком входят в него, включая границы.
- Период общего графика следует за периодом основного источника. Изменение периода
  любого источника проверяется против всех зависимых общих графиков.
- Удаление используемого источника блокируется с перечислением зависимостей.
  Удаление общего графика сохраняет исходные графики.
- Видимость сотрудникам по умолчанию выключена. При включении общий график целиком
  доступен активным сотрудникам с текущей должностью из любого источника.
  Участие в исходном графике не требуется; доступ к нему этим не предоставляется.
- Таблица группируется по источникам. Повторяющиеся сотрудники и исторические
  строки сохраняют отдельную идентичность. Ячейки вне периода источника отличаются
  от пустых ячеек внутри периода.
- «Смена сегодня» использует дату ресторана и остаётся доступной без смен.
- Открытое представление обновляется каждые 30 секунд, при возвращении на страницу
  и по кнопке «Обновить». В скрытой вкладке запросы приостанавливаются.

## Реализация

API: `/api/restaurants/{restaurantId}/common-schedules`; GET списка и одного
представления, POST создания, PUT настроек, DELETE с параметром `version`.
Для PUT требуется актуальная версия настроек.

`ScheduleContentMapper` используется обычными и общими графиками: фильтрация
участников, исторические ключи и формат содержимого остаются одинаковыми.
Общий API не возвращает историю, владельцев, пожелания или заявки источников.
Чтение одного общего графика выполняется в транзакции REPEATABLE_READ.

Операции изменения состава, удаления и изменения периодов сериализуются через
существующий `RestaurantLifecycleMutex`. Источники блокируются по возрастанию ID.
Миграция V134 создаёт `common_schedule` и `common_schedule_source`. Отложенные
ограничения позволяют переставлять источники и удалять ресторан каскадно,
сохраняя проверку уникальности и ссылочной целостности при завершении транзакции.

## Проверки

- `CommonScheduleServiceTest`: периоды, публикация, доступ, версии, защита
  источников, актуальные смены и исторические строки.
- `CommonSchedulePersistenceTest`: сохранение порядка, перестановка источников,
  увеличение версии, обновление смен после повторного чтения и удаление ссылок.
- `commonSchedule.test.ts`: сортировка, вложенность периодов, состав сегодня,
  повторяющиеся сотрудники и таблица без средств редактирования.
- `common_schedule_regression.sql`: PostgreSQL-проверка V134 в изолированной
  схеме с ROLLBACK. Перед запуском маркер `-- APPLY V134 HERE` заменяется текстом
  миграции. Проверяются удаление источника, уникальность, перестановка и каскады.

После обновления приложения Flyway должен применить V134. Проверочный SQL
не применяет миграцию к рабочим таблицам.
